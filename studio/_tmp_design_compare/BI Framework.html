Catalog anatomy — per KPI entry

  • id — unique dot-notation identifier
  • definition — business definition (prose)
  • formula — calculation logic (DAX stub)
  • unit — format / unit of measure
  • owner — domain owner
  • kpi_role — strategic / diagnostic / supporting
  • technical.lineage — required fact/dim columns
  • technical.depends_on_measures — measure dependencies
  • dax_name — Power BI measure name

KPI roles

  • strategic — Golden Thread KPIs, exec-visible, drive steering decisions
  • diagnostic — explain deviations in strategic KPIs (e.g. PVM effects)
  • supporting — intermediate calculations referenced via depends_on_measures, e.g. sales.price.list.amount
  • Supporting KPIs must appear in orchestration.influencing_kpi_ids in the Bracket — the measure generator emits them in dependency order
  • SSOT rule: KPI meaning lives only in core/kpi_catalog/ — never redefine in reports, brackets, or factsheets

Use Case Anatomy

Every use case has two representations: prose for humans, YAML for machines.

MD
Business_Factsheet.md — human layer
  • YAML frontmatter
    id, factsheet_type: business, domain, status
  • Business decision
    What decision does this use case enable? Prose description for domain leads.
  • KPI references
    KPI IDs only — e.g. sales.net_sales.amount. Never redefine KPI meaning.
  • Action references
    Which actions follow from deviations? Referenced by action code ID.
  • Prose only
    No DAX, no YAML config, no schema logic. Pure business context.
YAML
UseCase_Bracket.yaml — machine layer
  • orchestration
    KPI IDs, action code IDs, influencing KPIs, measure generation config
  • governance
    Owner, review cycle, data contract refs, refresh schedule
  • value_driver_model
    Driver tree: strategic KPI → diagnostic KPIs → supporting KPIs
  • ux_layout
    Page type (T1–T4), visual hierarchy, slicer configuration
  • action_code_ids
    Must be updated when adding/changing action code references

Action Codes

KPI deviation triggers governed action recommendations — reports surface them dynamically.

1
KPI Deviation
A strategic or diagnostic KPI crosses its threshold — plan miss, trend break, or benchmark breach.
sales.net_sales.delta_pct.plan < –5%
→
2
Trigger Evaluation
The action code's trigger logic evaluates: threshold, trend direction, impact category. Defined in YAML.
trigger: threshold_breach · impact: margin
→
3
Action Code YAML
The action code defines the recommendation: concrete steps, owner, expected impact, linked KPI IDs.
action_id: C-M1.1 · kpi_ids: [sales.net_sales.amount]
→
4
Report Surface
Reports display the action recommendation in the action panel (T4 Detail page). Dynamic — no hardcoded copy.
→ Initiate price review for top-10 customers

Action Code schema

  • action_id — unique ID (e.g. C-M1.1)
  • kpi_ids — all KPI IDs must exist in catalog
  • trigger — threshold, trend, or benchmark condition
  • impact_category — margin / revenue / cost / service
  • execution_steps — concrete next actions
  • Schema: tooling/generator/schemas/action_code.schema.json

Organization

  • Stored in core/action_codes/ organized by domain folder
  • Referenced in UseCase_Bracket.yaml → orchestration.action_code_ids
  • KPI IDs in action codes are validated against catalog at Stage 1
  • Skill: add-action-code-and-wire-up — creates and wires up in one step

Visualization Rules

Binding standards — not guidelines. Primary source: core/strategy_operating_model/operating_model/ux_design_system.md

Line + Area
Trend over time. Plan/LY as reference lines. Gap shaded for deviation.
Waterfall
Variance decomposition. PVM bridge. Floating bars per driver.
Bar (horizontal)
Ranking and cross-sectional comparison. Sorted by absolute impact.
100% Stacked Bar
Composition and share. Replaces pie/donut for part-to-whole.
Pie Chart
Never used. Use 100% stacked bar instead.
Donut Chart
Never used. Use 100% stacked bar instead.
KPI Card
3-second layer. Value + delta vs Plan + delta vs LY. Signal-first.
Matrix Table
300-second layer. Gap decomposition, drill-down, export.
Rule 1 — Slicers
Maximum 3 slicers per page
Each page may have at most 3 slicers. The active filter state must always be visible — readers must see what they are looking at without hunting for filter context. Standard slicer set: Date, Region/Channel, Product Category.
Author: Florian Haferkorn · Analytics Strategy-to-Action Framework
Source: ux_design_system.md §5.1 Normative UX Standards — Components · COM-001 Business_Factsheet.md §5.3 Required Slicers
Role owner: Commercial Controlling Lead
Rule 2 — 3-30-300 layer separation
Three distinct decision horizons per use case
3 s: KPI cards — immediate status signal, traffic-light deltas vs Plan and LY.
30 s: Main visuals — waterfall, trend, bar ranking, GM% bars with reference lines.
300 s: Detail table, gap decomposition, action recommendations (T4 prescriptive page).
Author: Florian Haferkorn · Analytics Strategy-to-Action Framework
Source: ux_design_system.md §4 The 3-30-300 Design Model · reporting_principles.md §5 Progressive Disclosure (3–30–300) · golden_thread_strategy_to_action.md §6 Measures → Reports
Role owner: CCO / Head of Sales · Commercial Controlling Lead
Rule 3 — Reference lines
Reference lines wherever targets or thresholds exist
All bar and line charts that compare against a plan, target, or guardrail must include a reference line at the target value. The deviation between the bar and the reference line must be visually detectable without reading numbers. South Europe GM% guardrail breach (30%) is one example.
Author: Florian Haferkorn · Analytics Strategy-to-Action Framework
Source: ux_design_system.md §5.1 Normative UX Standards — Components · reporting_principles.md §4 Actionability First · COM-001 Business_Factsheet.md §5.2 30-Second Layer (Notes: Guardrails)
Role owner: Commercial Controlling Lead
Rule 4 — 2-page report structure
Every use case delivers exactly 2 report pages
Page 1 — Overview (T1/T2): KPI cards + trend + waterfall + ranking + GM% comparison.
Page 2 — Detail (T3/T4): Slicer pane + matrix table + smart narrative + action panel. Page types T1–T4 are configured in UseCase_Bracket.yaml → ux_layout.
Author: Florian Haferkorn · Analytics Strategy-to-Action Framework
Source: AGENTS.md — Report Page Structure (Overview + Detail) · ux_design_system.md §5.3 Navigation · COM-001 Business_Factsheet.md §5 3-30-300 Page Layout (Mandatory)
Role owner: CCO / Head of Sales · Sales Leadership Team
Rule 5 — Forbidden chart types
No pie charts. No donut charts. Anywhere.
Pie and donut charts are explicitly prohibited. The human eye cannot accurately judge arc area — this introduces systematic reading errors in decision-making contexts. For part-to-whole composition, use 100% stacked bars: the area differences are readable along a shared baseline.
Author: Florian Haferkorn · Analytics Strategy-to-Action Framework
Source: ux_design_system.md §5.1 Normative UX Standards — Components: "Pie and donut charts are not used. 100% stacked bars replace split pie representations." · reporting_principles.md §6 Cognitive Simplicity
Role owner: Analytics Enablement Lead
Rule 6 — Layout & density
Controlled visual density — hierarchy via layout, not labels
Consistent spacing, padding, and alignment are mandatory across all reports. Hierarchy must be visible from layout geometry alone — a user glancing for 3 seconds should know immediately whether to stay or drill deeper. Visual density is actively managed to prevent cognitive overload.
Author: Florian Haferkorn · Analytics Strategy-to-Action Framework
Source: ux_design_system.md §5.2 Layout and Density · §3 UX Principles (Minimalism, Hierarchy, Clarity) · reporting_principles.md §6 Cognitive Simplicity
Role owner: Analytics Enablement Lead
Rule 7 — Navigation predictability
Consistent page structure across all use cases
All reports in all domains follow the same navigation contract: Overview → Detail. Tab labels, page order, slicer placement, and filter bar behavior are identical across COM, FIN, OPS, SCM, and XD. Users re-use learned patterns — not re-learn per use case.
Author: Florian Haferkorn · Analytics Strategy-to-Action Framework
Source: ux_design_system.md §5.3 Navigation · §2 Design Scope · reporting_principles.md §7 Consistency Across Domains · §8 User-Centric Design
Role owner: Analytics Enablement Lead · CCO / Head of Sales
Rule 8 — Color semantics
Fixed color-to-meaning mapping — no exceptions
Positive deviations: Mint #47D7AC. Negative deviations: Sunset #F8485E. Neutral / reference: Petrol/Nightfall. Plan line: dashed Mint. LY line: dashed Limestone. These mappings are fixed across all reports — red is never used for a positive value.
Author: Florian Haferkorn · Analytics Strategy-to-Action Framework · Nagarro Brand Design System
Source: ux_design_system.md §3 UX Principles (Consistency) · reporting_principles.md §7 Consistency Across Domains · Nagarro Brand Design System — colors_and_type.css (Mint #47D7AC primary CTA, Sunset #F8485E alert)
