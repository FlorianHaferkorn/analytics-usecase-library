# fabric-powerbi-authoring.md — Power BI Semantic Model Authoring

> **Source**: `microsoft/skills-for-fabric` powerbi-authoring-cli/SKILL.md
> **Purpose**: Guidance for creating, managing, and deploying Power BI semantic models in Fabric via REST API.

---

## Critical Architecture: Two API Audiences

Two distinct API audiences are required for semantic model operations. Using the wrong one will silently fail authentication.

| Operation | API | Resource / Audience |
|---|---|---|
| Definition CRUD (create, read, update, delete model) | **Fabric Items API** | `https://api.fabric.microsoft.com` |
| Refresh, data sources, parameters, permissions, deployment pipelines | **Power BI Datasets API** | `https://analysis.windows.net/powerbi/api` |

Every `az rest` call must specify the correct `--resource` parameter.

---

## TMDL Structure Requirements

Semantic models require these mandatory parts:

| Part | Purpose | Required |
|---|---|---|
| `definition.pbism` | Connection settings (JSON format, version `"4.2"`) | Yes |
| `definition/database.tmdl` | Database properties — muss mit `database '<Name>'` beginnen, `compatibilityLevel: 1702` | Yes |
| `definition/model.tmdl` | Model properties — `defaultPowerBIDataSourceVersion: powerBI_V3` Pflicht für Import-Mode | Yes |
| `definition/tables/*.tmdl` | Per-table definitions (columns, measures, partitions) | ≥1 required |

> **Critical**: The API replaces entire definitions during updates — all parts (modified and unmodified) must be included. Omitted parts are deleted. Never include `.platform` metadata in update payloads.

> **TMDL-Syntax** für database.tmdl, model.tmdl, Direct Lake Entity Partitions, Calculation Groups, RLS-Rollen:
> → `tmdl-advanced-features.md`

## Must / Prefer / Avoid

### MUST DO

- Read `TMDL_Allowed_Subset.md` (Policies) **und** `tmdl-advanced-features.md` (Syntax) vor jeder TMDL-Generierung
- Always pass `--resource` parameter to `az rest` — falsche Audience = `401`
- Include `Content-Type: application/json` header on Power BI API POST/PATCH/PUT calls
- Base64-encode all TMDL content payloads before submission
- Poll long-running operations (LRO) to completion before proceeding — **`getDefinition` braucht `/result` am Poll-URL-Ende**
- Include ALL definition parts in updates (not just changed parts)
- Verify workspace has capacity assignment before creating models
- Für REST-Deploy: `byConnection` in `definition.pbir` nutzen — `byPath` wird von der Fabric API abgelehnt

### PREFER

- `createItemWithDefinition` (single POST) over create-then-update workflows — reduces round trips
- TMDL format over TMSL for text-based, diff-friendly definitions
- Route fine-grained changes (individual measures/columns) to `powerbi-modeling-mcp` if available
- Retrieve current definition before updating to avoid overwriting concurrent changes

### AVOID

- `updateDefinition` for small changes — inefficient full definition round-trip
- Report creation (separate definition format required — use PBIR)
- Manual `lineageTag` addition on new objects (auto-generated by system)
- `//` comments in TMDL (use `///` instead — enforced by PostToolUse hook)
- Hardcoded IDs (resolve dynamically via REST API)

## Workflow Pattern

1. Discover target workspace and verify capacity assignment
2. List existing semantic models to confirm name availability
3. Design star schema (fact and dimension tables)
4. Author TMDL files following syntax rules (see `TMDL_Allowed_Subset.md`)
5. Base64-encode all parts and submit via `createItemWithDefinition`
6. Poll LRO until `Succeeded`
7. Validate structure and test measures via DAX queries (`execute_dax.py`)
8. Configure refresh schedules, data sources, and permissions as needed
9. Deploy between pipeline stages using deployment APIs

## Command Structure (az CLI)

```bash
# Create model with definition
az rest --method post \
  --resource "https://api.fabric.microsoft.com" \
  --url "https://api.fabric.microsoft.com/v1/workspaces/$WS_ID/semanticModels" \
  --headers "Content-Type=application/json" \
  --body @/tmp/payload.json

# Trigger refresh (Power BI API — different resource!)
az rest --method post \
  --resource "https://analysis.windows.net/powerbi/api" \
  --url "https://api.powerbi.com/v1.0/myorg/groups/$WS_ID/datasets/$MODEL_ID/refreshes" \
  --headers "Content-Type=application/json" \
  --body '{"type":"Full"}'

# Get current definition (for update workflow)
az rest --method post \
  --resource "https://api.fabric.microsoft.com" \
  --url "https://api.fabric.microsoft.com/v1/workspaces/$WS_ID/semanticModels/$MODEL_ID/getDefinition?format=TMDL"
```

## Permission Troubleshooting

**Critical early-abort rule**: If `getDefinition` returns `404 EntityNotFound` on an item you can list AND the Power BI refresh API returns `403 Forbidden` with `"identity None"`:

1. **Stop immediately** — do not retry with different URL formats or parameters
2. The user almost certainly has only **Viewer** role
3. Verify: `GET /v1/workspaces/{id}/roleAssignments`
4. Resolution: Request **Contributor or higher** role

This combination of 404 + 403 is always a permissions issue, not an API usage issue.

## Base64 Encoding Pattern

```bash
# Encode a TMDL file for use in a definition payload
TMDL_CONTENT=$(base64 -w 0 definition/tables/Sales.tmdl)

# In payload JSON
{
  "path": "definition/tables/Sales.tmdl",
  "payload": "$TMDL_CONTENT",
  "payloadType": "InlineBase64"
}
```

## LRO Polling Pattern

```bash
# After a 202 response, poll until Succeeded
OPERATION_ID="<from x-ms-operation-id header>"
while true; do
  STATUS=$(az rest --method get \
    --resource "https://api.fabric.microsoft.com" \
    --url "https://api.fabric.microsoft.com/v1/operations/$OPERATION_ID" \
    --query "status" -o tsv)
  echo "Status: $STATUS"
  if [ "$STATUS" = "Succeeded" ]; then break; fi
  if [ "$STATUS" = "Failed" ]; then
    echo "Operation failed. Get details:"
    az rest --method get --resource "https://api.fabric.microsoft.com" \
      --url "https://api.fabric.microsoft.com/v1/operations/$OPERATION_ID/result"
    exit 1
  fi
  sleep 5
done
```

## Resolve Workspace and Model IDs

```bash
# Workspace ID by name
WS_ID=$(fab get "MyWorkspace.Workspace" -q "id" | tr -d '"')

# Model ID by name
MODEL_ID=$(fab get "MyWorkspace.Workspace/MyModel.SemanticModel" -q "id" | tr -d '"')

# Or via REST API (no fab dependency)
WS_ID=$(az rest --method get \
  --resource "https://api.fabric.microsoft.com" \
  --url "https://api.fabric.microsoft.com/v1/workspaces" \
  --query "value[?displayName=='MyWorkspace'].id" -o tsv)
```
